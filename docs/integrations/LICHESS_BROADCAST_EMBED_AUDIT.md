# Lichess Broadcast embed integration audit

**Audit:** LBC-0.1

**Observed:** 2026-08-15 04:00 EDT / 08:00 UTC
**Verdict:** **CONDITIONAL GO.** CAISSA can reuse the official Lichess Broadcast iframe with a small, centrally configured, provider-specific gateway. The sustainable default is the tournament-level iframe generated by Lichess, because it keeps one stable broadcast ID while Lichess selects the current round. A round-pinned iframe is also official and is appropriate when editorial intent requires a specific round or completed replay. LBC-0.2 must reselect a fresh event, prove the restrictive sandbox in its own cross-browser harness, and resolve the provider's narrow-mobile selected-game overflow before release.

## 1. Executive verdict

The official mechanism is sufficient without a CAISSA viewer, API client, polling loop, WebSocket, proxy, scraper, PGN parser, database, or round selector. Lichess's broadcast page itself generates both tournament-level and round-level iframe markup. The embedded document contains the event name, round state, Overview/Boards/Players tabs, game list, board, player names, ratings, results or clocks when supplied, notation, round controls, and a provider-owned link back to Lichess. It does not expose the full-page chat in the embed observed.

The integration is not an automatic featured-broadcast product. An operator must select and verify a Lichess broadcast. Tournament-level configuration reduces maintenance because the stable broadcast URL is documented as redirecting to the current round and the generated tournament embed selected the current round in observation. A pinned round remains pinned. CAISSA must calculate only a schedule window from separately verified UTC fields and must never infer "Live now" from iframe load, provider text, or the presence of clocks.

## 4. Exact URL and identity contract

For the pilot, the official page generated:

```html
<iframe
  src="https://lichess.org/embed/broadcast/gct-sinquefield-cup-2026/2sMqschv"
  style="width: 100%; aspect-ratio: 4/3;"
  frameborder="0">
</iframe>
```

and the selected-round form:

```html
<iframe
  src="https://lichess.org/embed/broadcast/gct-sinquefield-cup-2026/round-5/yjutpiJf"
  style="width: 100%; aspect-ratio: 4/3;"
  frameborder="0">
</iframe>
```

The current contracts are therefore:

```text
Tournament: https://lichess.org/embed/broadcast/{broadcast-slug}/{broadcast-id}
Round:      https://lichess.org/embed/broadcast/{broadcast-slug}/{round-slug}/{round-id}
Game view:  provider-owned navigation below the round URL; not a CAISSA config field
```

The initially proposed two-segment round pattern, `/embed/broadcast/{broadcast-slug}/{round-id}`, is not sufficient as a general current contract. It works for the official 2024 developer example but returned 404 for the pilot round when its round slug was omitted. LBC-0.2 must validate only one of the exact generated shapes and must not synthesize URLs from names.

The broadcast ID (`2sMqschv`) is the durable tournament identity CAISSA should preserve. The round ID (`yjutpiJf`) is required only for pinned-round mode. Slugs are validated URL components, not identities. Chapter/game IDs are runtime provider links and must never enter CAISSA configuration or analytics.

The tournament embed returned HTTP 200 without redirect and displayed Round 5. The round embed returned HTTP 200 and stayed on Round 5. Invalid broadcast/round IDs returned 404. The completed official 2024 example remained HTTP 200, establishing replay persistence at the observation time.

## 5. Broadcast, tournament, round, and game behavior

- **Directory:** `/broadcast` is a discovery page, not an embed and not an automatically selected CAISSA product.
- **Broadcast/tournament:** one event record with shared metadata and multiple rounds. Its official share URL and tournament embed use the broadcast ID.
- **Round:** one scheduled segment with its own round ID and optional human slug. The pinned embed does not advance.
- **Game/chapter:** selected inside the provider viewer. CAISSA must not own or persist this selection.
- **Future rounds:** the official share guidance promises that the broadcast URL redirects to the current round; the generated tournament embed was also round-selecting in observation. Because the documentation does not separately promise its rollover timing, LBC-0.2 must verify rollover against a multi-round event and retain an official-link fallback.
- **Finished event:** completed rounds and the historical official example remain usable for replay. CAISSA may keep the iframe in `completed/replay` state.

## 8. Editorial maintenance model

Recommended mode: an operator selects one public Lichess broadcast, copies the exact generated **tournament iframe**, verifies event provenance/schedule, and commits one immutable record. The tournament URL minimizes round maintenance. If editorial intent is a specific round, set `selectionMode: 'round'` and configure the exact generated round URL; an operator must update it for each new round.

There is no documented automatic featured broadcast or embeddable directory. CAISSA must not scrape the directory or use an API to choose an event. Disable or replace stale configuration through a normal reviewed release. No admin dashboard is justified.

## 9. Proposed canonical configuration

Reuse the validation/status foundation of `CaissaFeaturedExternalTournament@1.0.0`, but advance it rather than weakening its ChessBase URL invariants. A provider-neutral record plus a small literal Lichess adapter is sustainable; the released ChessBase record should remain behaviorally unchanged.

Proposed conceptual schema: `CaissaFeaturedExternalTournament@2.0.0`.

Required common fields:

- `schema`, `id`, `provider: 'lichess-broadcast'`, `enabled`;
- `displayName`, `organizerName`, `location`;
- `startsAt`, `endsAt` as explicit UTC instants; `eventTimezone` as an IANA zone;
- `providerEventUrl`, `frameUrl`, `verifiedAt`, `evidenceUrls`;
- `selectionMode: 'tournament' | 'round'`.

Lichess adapter fields:

- `broadcastId`, `broadcastSlug`;
- `roundId` and `roundSlug` required only in round mode;
- optional `roundName` as verified display copy, never URL authority.

Do not duplicate game IDs, chapter IDs, player names, ratings, results, clocks, PGN, standings, chat, or provider live state. Organizer/site/location/schedule are organizer-controlled facts surfaced by Lichess and must carry evidence; iframe/broadcast/round identity is Lichess-controlled; CAISSA controls only selection, enabled state, verification time, and bounded presentation copy.

## 10. Truthful UTC status model

Reuse these parent-owned states:

- `configuration-error`: validation fails or disabled record is unexpectedly mounted;
- `upcoming`: `now < startsAt`;
- `coverage-window`: `startsAt <= now < endsAt`;
- `completed/replay`: `now >= endsAt`; keep a verified working iframe as replay;
- `unavailable`: bounded provider-load failure overrides the schedule state;
- `loading` and `document-loaded`: transport/lifecycle facts only;
- `retrying`: one explicit user retry replacing exactly one iframe.

Exact start belongs to `coverage-window`; exact end belongs to `completed/replay`. Convert verified organizer-local instants to UTC once in configuration and display both the named event timezone and visitor-local time where useful. Date-only schedules cannot justify intraday `upcoming` or `coverage-window`; either obtain verified times or disclose that only the published event dates are known. Never infer active play from `load`, clocks, result controls, provider wording, or current date. Warn when `verifiedAt` exceeds a release-defined freshness threshold. Provider failure changes presentation to unavailable but does not rewrite schedule truth.

## 11. Security and sandbox

The exact parent frame origin is already present for Lichess TV:

```text
frame-src ... https://lichess.org;
```

LBC requires no new global CSP origin. Do not add `lichess1.org`, wildcards, or LBC-driven permissions to `script-src`, `connect-src`, `worker-src`, `img-src`, or other directives. The pre-existing global `connect-src https://lichess.org` belongs to unrelated functionality; the Broadcast parent must not use it.

Candidate iframe policy:

```html
sandbox="allow-scripts allow-same-origin"
referrerpolicy="no-referrer"
```

No `allow` feature permissions are required. Omit forms, popups, top navigation, downloads, clipboard, autoplay, fullscreen, camera, microphone, and geolocation. The observed embed has one `_blank` provider link; the narrow sandbox should contain it while CAISSA supplies its own official link outside the frame.

Direct official embeds returned 200 with no `X-Frame-Options` denial, CSP response header, or `Set-Cookie` header in the bounded HTTP observation. The exact sandbox could not be executed in the available controlled browser because its safety policy rejected the local harness URL. The same-origin Lichess TV runtime is certified with this sandbox, but that is supporting evidence, not proof for Broadcast. Cross-browser sandbox compatibility is therefore a hard LBC-0.2 gate.

The parent needs no Lichess script, API, polling, WebSocket, Worker, OAuth, cookie, fetch, storage, or `postMessage` bridge. Frame URL validation must reject credentials, ports, fragments, unknown origins, malformed IDs, arbitrary query keys, and game/chapter paths.

## 12. Privacy and provider boundary

In a fresh anonymous embed observation, no local-storage or session-storage keys, form, login/signup link, chat UI, or `postMessage` reference was exposed by the embedded round. No `Set-Cookie` response was observed. One provider-owned `_blank` link opened Lichess. These are point-in-time observations, not permanent guarantees; LBC-0.2 must repeat them.

The full broadcast page can contain provider-moderated chat and account affordances, but the official embed observed did not. CAISSA must not read or transmit usernames, ratings, moves, results, game/chapter/round IDs, chat, or account state as analytics. CAISSA's existing pathname-only analytics remains outside the iframe and records only the CAISSA route. Lichess controls all activity inside its cross-origin frame.

Do not transform-scale. The 320px provider overflow must be explicitly accepted with contained internal scrolling or must block release if controls/board become unusable.

## 14. Accessibility

CAISSA owns one H1, a labelled viewer region, visible schedule status, polite loading status, alert-only error, descriptive iframe title (proposed: `Lichess Broadcast: {event}, {round-or-current-round}`), retry focus management, official-link fallback, attribution landmark, drawer behavior, and keyboard reachability outside the frame.

The embed exposes semantic event/round headings, tabs, buttons, a game-count selector, player links, results, and an "Open in Lichess" link. It also offers Lichess's blind-mode control on the full page, but cross-origin internals and every keyboard/focus path cannot be certified by CAISSA. Do not claim the provider viewer is fully accessible. LBC-0.2 must test tab entry/exit, visible focus, selected-game navigation, internal scrolling, zoom, and mobile drawer isolation in Chromium, Firefox, and WebKit.

## 15. Error model

Validated observations:

- exact tournament and round configurations: HTTP 200;
- omitted required round slug for the pilot: 404;
- malformed/unknown broadcast and round IDs: 404;
- completed round and 2024 historical example: HTTP 200 replay;
- iframe load alone cannot distinguish valid content from a provider 404 page.

LBC-0.2 must simulate invalid configuration before iframe creation, malformed URL, wrong origin, missing/deleted round, provider block, offline, timeout, and sandbox incompatibility locally. The controller should expose loading, document-loaded, schedule state, completed/replay, unavailable, configuration-error, retrying, and an always-visible official-link fallback. Retry must clear one timer/listener generation and replace the old iframe, leaving exactly one frame and no automatic loop.

## 20. Known limitations

- manual editorial event selection and schedule verification are required;
- tournament-embed round rollover is observed and consistent with official sharing guidance, but its exact timing is not separately documented;
- `iframe.onload` cannot validate broadcast content or active play;
- date-only public schedules are insufficient for exact UTC status;
- provider content and availability can change independently;
- the provider owns internal controls, engine/evaluation, links, and accessibility;
- restrictive sandbox compatibility remains unproven for Broadcast in this audit environment;
- selected-game layout has internal horizontal overflow at 320px;
- full-page chat exists, although it was absent from the observed embed;
- historical replay persistence is observed, not guaranteed indefinitely;
- Firefox revision 1538 retains the separately documented FFX-1.0 target-crash limitation.
