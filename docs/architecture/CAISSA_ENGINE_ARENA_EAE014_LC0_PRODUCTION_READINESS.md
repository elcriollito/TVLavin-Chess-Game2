# CAISSA Engine Arena — EAE-014 Lc0 production-readiness review

Review target: certified Preview source `8b047da01c7aaf19594b7c828fe4d296679de050`, Preview deployment `dpl_FtJKjJf7xuheA5DHjWNdkyPEcQHd`. This is a **decision and design document**, not production authorization. No main merge, production deployment/schema/DNS/header change, provider activation, or broad Engine Details UI is part of EAE-014.

## Decision and release boundary

**`LC0_PRODUCTION_HOLD`**. The two-origin browser architecture and scoped relay identity model are credible, and the EAE-013A Preview reliability evidence is strong. The *current implementation* is deliberately Preview-only and is not a deployable production candidate: it rejects `VERCEL_ENV=production`, requires `.vercel.app` origins and the pinned staging database, uses a nonrenewable 120-second session limit, has no scheduled cleanup, permits an expensive INFO/SSE polling envelope, and has no production kill switch or dedicated production origin. License/source-offer packaging and full release-chain integrity also require sign-off. These are resolvable gates; no source-backed evidence suggests Lc0 must be abandoned.

**Season recommendation: YES, ship Stockfish 18 Lite and Stockfish 19 Lite before Lc0**, through their own normal release approval. Their independent certification should not wait on this Preview-only Lc0 relay. Do not ship all three together solely for season symmetry.

The recommended first Lc0 release, *after the gates below pass*, is a controlled opt-in desktop Experimental rollout, not a general/mobile release. The evaluator remains Stockfish; at most one Lc0 participant joins a competition. The visible participant name remains **“Lc0 — Maia 1100 (Experimental)”**; Maia 1100 must not be advertised as maximum-strength Lc0.

## Security and trust model

The main Arena is a real CAISSA/Clerk-authenticated user. The isolated engine page receives **no Clerk token**: the main adapter opens it with a one-use, 30-second claim capability in a URL fragment, severs opener access, and the engine clears the fragment before exchanging it for a session-scoped bearer (`isolated-browser-runtime-adapter.js:272-284`, `engine/client-source.js:98-120`, `durable-broker.mjs:178-191`). The broker stores session-bound credential hashes, not plaintext tokens. Engine credentials cannot create sessions or issue main-role commands; user ownership and engine authority are separate (`api/eae011.js:108-145`, `durable-broker.mjs:147-191`). Termination deletes the session; successful CLEANUP revokes the engine credential. Credentials must never be copied between origins or logged.

The route enforces action/method/Host and exact POST Origin; no wildcard CORS exists in Preview (`api/eae011.js:9-39`). Non-browser clients can forge an Origin header, so authentication/capability checks—not Origin alone—remain the authority. Phase, sequence, search ID, cursor, lease epoch, BESTMOVE and CLEANUP evidence checks are enforced in `durable-broker.mjs:194-437`. Staging session, creation-window and audit tables have RLS enabled and no `anon`/`authenticated` grants; a read-only staging query on 2026-09-22 found zero active/expired relay rows and 3,828 audit rows. Supabase security advisors showed only the INFO “RLS enabled, no policy” notice for these intentionally service-role-only tables, not a client grant; [Supabase documents](https://supabase.com/docs/guides/database/postgres/row-level-security) the distinction between grants and RLS. The staging database is not production.

| Threat / potential impact | Existing Preview control | Remaining exposure and production requirement |
| --- | --- | --- |
| Session hijack, cross-user access, cross-session leakage | Clerk bearer verified server-side; owner ID checked on each main action; engine credential hashed with session ID | Re-test BOLA/IDOR on production routes and across tenants; never authorize by caller-chosen `competitionId` alone. |
| Claim theft, reconnect-credential theft | One-use 30 s fragment claim; no opener; fragment removed; engine bearer scoped to one session; revocable on cleanup/expiry | A compromised isolated origin or leaked claim can race/impersonate that session. Do not put secrets in telemetry, referrers or URLs beyond the transient fragment; rotate/revoke on suspicious activity. |
| Command replay, stale BESTMOVE, late CLEANUP | Monotonic sequences, command claim, search IDs, phase/epoch checks and cleanup evidence | Repeat adversarial race tests on production topology and long games; keep stale-generation callbacks non-destructive. |
| Origin spoofing, CSRF, CORS errors | Exact Host/POST Origin, bearer auth, no permissive CORS in Preview | Three-origin production relay needs allowlisted exact origins, preflight/Vary handling, no cookies, and negative cross-origin tests. Origin headers are not credentials. |
| Payload abuse and session-creation floods | 4 KiB parsed request, 2 KiB command, 1 KiB INFO, bounded PV/events; staging 20 creates/min and 10 live sessions/user | Cap raw ingress before JSON parsing; lower initial per-user limits; add IP/global budgets, WAF/edge throttles and admission control. Current per-user limits are too generous for launch. |
| INFO floods and expensive rejected requests | Low-priority journal coalescing; real client emits at most about 6.7 INFO/s; broker nominally permits 100 INFO/s/session | **Production gate:** accepted INFO rewrites full JSONB state; over-limit INFO/reconnect `429` paths still CAS-write before returning error (`durable-broker.mjs:122-140,285-297,368-376`, `store.mjs:94-99`). Coalesce before persistence, reject before CAS, and load-test per-owner/global budgets. |
| SSE read amplification / DoS | Authenticated, leased streams; 250 ms polling; 120 s Preview cap | Two streams cause ~8 Postgres SELECTs/s per session even when idle (`api/eae011.js:68-88`, `durable-broker.mjs:409-426`). Replace with adaptive/backoff or push design and prove capacity before release. |
| Lease races, relay-state corruption, worker crash | EAE-013A epoch guard, versioned CAS/delete, reasoned tombstones, fail-closed worker cleanup | Longer sessions, function turnover, storage faults and sustained concurrency need staged fault/load drills; forced termination is an abnormal metric, never normal cleanup. |
| Dependency or asset compromise, network tampering | Source/toolchain/patch/network hashes pinned; manifest and six assets checked before READY; same-origin CSP | The executed `lc0-worker.js` and client entrypoint are **outside** the six-asset hash list, and verify-then-load may refetch URLs (`engine/client-source.js:34-61,123-130`). Bind the entire executed release to immutable content-addressed bytes/deployment, retain hashes and generate provenance/SBOM. |

The static source review did **not** establish a cross-user auth bypass, claim replay, Clerk-token transfer to the engine page, direct XSS, or SQL injection. This is not a penetration test or a claim that other deployed configurations are safe. A caller knowing a victim session ID could consume its eight invalid-claim attempts before the correct claimant arrives (`durable-broker.mjs:178-191`); the 256-bit random ID makes that prerequisite unlikely, but production should avoid making a valid claim fail solely because prior guesses were wrong. The full scoped scan was not a review of all generated/minified WASM or all unrelated site code.

## Proposed production topology and session policy — not implemented

Keep `www.caissa-chess.org` **non-isolated**. Use `lc0.caissa-chess.org` as a dedicated, top-level, desktop Lc0 runtime origin: one static/runtime-only Vercel project, no interactive Clerk, payments, unrelated app routes, Supabase service key or www cookies. Its HTML and workers get COOP `same-origin`, COEP `require-corp`, CORP `same-origin`, a narrow `script-src 'self' 'wasm-unsafe-eval'`, `worker-src 'self'`, `connect-src 'self' https://relay-lc0.caissa-chess.org`, no frames/forms, and no-referrer. This isolates SharedArrayBuffer/pthreads without changing whole-site headers. No DNS or project was configured here.

Prefer a **third, dedicated relay project** at `relay-lc0.caissa-chess.org`: both www (Clerk bearer) and the engine page (scoped engine bearer) call it over HTTPS with exact origin allowlisting and CORS; its server-only least-privilege database credential and Clerk verifier never reach either browser. The main www project owns Arena UI/Stockfish evaluator and an authoritative provider flag; the Lc0 project serves only pinned runtime/network/worker bytes; the relay project owns API/admission/metrics and the production relay database. This is stronger blast-radius separation than the current two aliases of one Preview project. The present same-origin `/api/eae011` client, `.vercel.app` origin guard, and staging-store pin must be refactored and verified for this topology—**do not remove Preview gates in place and call it production**. Alternative two-project routing needs an explicit proxy/CORS/secret-boundary review; it is not implicitly approved.

Proposed lifecycle: create a session tied to a server-authorized Arena competition and Lc0 participant, not an arbitrary submitted competition label. Keep it renewable only while that competition/game is active and both main and engine liveness is proved using **server-authoritative time**. A design target is heartbeats every 5 s, a 30 s liveness deadline, and a 15–20 s transport-reconnect grace; disconnect changes UI state immediately but a single lost SSE response does not revoke ownership. Pause keeps heartbeats alive. After a missing owner or engine heartbeat beyond the deadline, fail closed with a named reason and local worker cleanup; avoid automatic Stockfish substitution. Give an unclaimed session ~60 s; give an abandoned/non-competition idle session ~5 min; paused competition idle needs an explicit UX timeout (proposed warning at 8 min, release at 10 min), not the current `idleMs=30_000`. Maintain a bounded absolute cap **per game**, derived from the product's maximum permitted game duration plus cleanup grace; a provisional 2-hour cap is appropriate only if a game is capped below that. Rotate/clean a Tournament participant at game boundaries before that cap, or prove a longer bound and user warning. Do not impose a nonrenewable 120 s TTL on an active valid game. These numbers are design targets requiring long-game/load tests, not measured production settings.

Keep the corrected STOP ACK **warning at 3 s, timeout at 10 s**: the 100-cycle STOP p95 was 1.907 s, and pre-fix 2.5 s incorrectly deleted a valid `STOPPING` session. At 3 s show “Stopping engine…” and record slow-STOP telemetry; at 10 s report `STOP_TIMEOUT`, revoke the session with a reasoned tombstone, stop/force-clean locally if necessary, and abort the affected participant/game under the published failure policy. Never manufacture BESTMOVE/STOPPED. The distinct current five-second ACKed-STOP→BESTMOVE result deadline also needs long-game/load validation; it must not be silently conflated with the 10-second ACK policy.

Production Postgres should be a **new, isolated namespace/project** or separately permissioned database, not changes to existing CAISSA application tables. Design-only migration: `lc0_relay_sessions` (session ID PK, authoritative owner/competition/role, created/renewed/absolute/lease deadlines, version, bounded protocol JSONB), `lc0_creation_windows`, and sanitized `lc0_session_audit` tombstones; indexes on owner+live deadline, deadline for GC, and audit recorded time/session ID. Preserve atomic create limits and versioned compare-and-swap/delete with reason; add explicit expiry/owner validation to all reads and writes. INFO must not generate a full-row write per line. RLS and revoked `anon`/`authenticated` grants are required even for server-only tables; use narrowly granted service operations and never expose the service role to a browser. The staging advisor's no-policy INFO notice is consistent with service-role-only access, but production grants must be independently tested. [Supabase's RLS guidance](https://supabase.com/docs/guides/database/postgres/row-level-security) requires reviewing both grants and policies.

Run an idempotent, observable **scheduled cleanup** (e.g. [Supabase Cron/pg_cron](https://supabase.com/docs/guides/cron)) every minute in bounded batches using database time and row locking/CAS, plus request-time expiry. It must purge abandoned sessions/creation windows and prune sanitized tombstones after an approved retention window (proposed seven days for incident review, subject to privacy policy); preserve counters before pruning. Alert on job failures, lag, expired-row count, and audit `UNKNOWN`. No cron job or production table was created in EAE-014. Rollback migration is a design: disable admission, drain/revoke active sessions, preserve audit/incident evidence and a backup, then remove **only** the new Lc0 schema/jobs after retention and verified zero dependency. Never roll back SF18/SF19 or pre-existing production tables as part of Lc0 rollback.

## Resource, bandwidth and cost model

Lc0 search/inference runs **in the user's browser**, CPU/WASM with SIMD, SharedArrayBuffer and pthread support; it does not create an Lc0 server-compute or license-fee meter. The configured Lc0 and ORT search thread counts are one each, but the Emscripten build preallocates four pthread workers: EAE-012 observed up to five total workers per isolated runtime. CPU, memory pressure, battery/thermal behavior and minimum RAM need real desktop measurements; no memory budget is certified. Initial admission should be one active Lc0 session per user and one Lc0 participant per competition, with an explicit small global cap until measured.

The six manifest-listed assets total **24,472,302 bytes**; bundled `client.js` and executed `lc0-worker.js` add 311,253 bytes, or **24,783,555 bytes (~24.8 MB) of unique files** before HTML, headers and possible duplicate downloads. The network alone is 1,313,193 bytes with SHA-256 `e1cf1cd0c96b8a4fa6a275f4b9fd54ed1ffebf9fe44641b9fceded310e9619c4`. This is **not** measured wire traffic: compression may reduce it, while current `Cache-Control: private, no-store` and verify-then-runtime loading may redownload assets (`vercel.json:229-238`, `engine/client-source.js:34-61`, `lab-runtime.js:101-162`). Production should use versioned/content-addressed immutable files with long immutable cache headers, a complete release manifest (including executed client/worker), and verify the actual executed bytes; keep HTML and credential responses noncacheable. Measure cold/warm HAR on Chrome/Edge before setting a bandwidth budget.

Current idle relay cost scales sharply because two SSE streams each poll the database every 250 ms; two client heartbeats each occur every 1.5 s. The table is a **code-derived illustration, not a capacity test or dollar quote**. Cold bytes multiply the unique-file size only; real transfer can differ.

| Simultaneous sessions | SSE streams | Idle session-row reads/s | Heartbeat state writes/s | Unique cold assets if all first-load |
| ---: | ---: | ---: | ---: | ---: |
| 10 | 20 | ~80 | ~13 | ~248 MB |
| 100 | 200 | ~800 | ~133 | ~2.48 GB |
| 500 | 1,000 | ~4,000 | ~667 | ~12.4 GB |
| 1,000 | 2,000 | ~8,000 | ~1,333 | ~24.8 GB |

Accepted INFO can add up to **100 full JSONB CAS writes/s/session** at the current broker limit, even though the honest engine client emits at most about 6.7/s and the UI presents at most 4/s; a malicious credential holder can bypass client pacing. EAE-012 observed 110 raw stdout INFO lines but only 32 normalized messages across 20 fresh lifecycles; this is not a per-second production traffic distribution. Recommend <=4 normalized relay updates/s/session, latest-value coalescing **before** durable persistence, no high-frequency PV history in Postgres, bounded event journal, and a tighter aggregate owner/global write budget. STOP/ACK/BESTMOVE/CLEANUP must remain priority messages, not coalesced away.

Billing meters to validate with a tenant-specific load profile are Vercel Function invocations, active CPU/provisioned memory for long-running SSE, network transfer/cached asset transfer, Supabase PostgREST reads/writes, database compute/storage and egress. [Vercel's current Function pricing](https://vercel.com/docs/functions/usage-and-pricing) distinguishes CPU from memory reserved during I/O, and [function-duration limits](https://vercel.com/docs/functions/configuring-functions/duration) can terminate a long SSE response; the client must reconnect safely before that limit. [Supabase compute](https://supabase.com/docs/guides/platform/manage-your-usage/compute) is charged for the database instance, while [egress](https://supabase.com/docs/guides/platform/manage-your-usage/egress) has its own meter. No exact monthly dollar amount is asserted without the project's plan, region, cache hit rate, session length and measured call/byte traces. **Do not admit 100/500/1,000 concurrent sessions based on the Preview soak.**

## Browser, UX and competition policy

Initial target **supported after production smoke:** current Chrome and Edge desktop releases on capable machines. Evidence is Chromium Preview certification plus one physical installed-browser full lifecycle in each, not a broad OS/version matrix. Treat Firefox desktop as **experimental/unverified for Match/Tournament** (only isolation/SAB page check passed), and Safari desktop as **unverified/excluded from first rollout**. Android Chrome and iOS Safari are **unsupported for initial Lc0**: mobile was deliberately unavailable in Preview and has no runtime/resource certification. Browser feature detection must verify COI, SAB, SIMD and actual worker/runtime initialization; user-agent names alone cannot grant support. Re-run Chrome/Edge real Match both colors, Tournament, window-close, network-loss and long-game tests on the eventual production topology before marking them supported.

No browser has *production* support today because Lc0 is not deployed there. The proposed first-rollout matrix is: Chrome desktop and Edge desktop **SUPPORTED only after production smoke**; Firefox desktop **EXPERIMENTAL pending full lifecycle certification**; Safari desktop **UNSUPPORTED until tested**; Android Chrome and iOS Safari **UNSUPPORTED for initial release**.

The UI needs visible states: **Connecting → Verifying engine → Loading network → Initializing → Ready → Searching → Stopping → Cleaning up**, with **Disconnected** (short reconnection grace) and **Failed** (terminal) branches. Use the measured 4–6 s Preview p95 selection→READY and ~2 s STOP/cleanup as initial expectations, not guaranteed SLAs. A spinner plus phase text and a bounded timer should prevent a frozen-looking page. Provide an explicit “Cancel Lc0 setup” action. Distinguish slow but live from expired/failed; never show READY merely because the claim succeeded.

Choose a **visible, minimal utility companion window** on `lc0.caissa-chess.org`, opened only after a clear user gesture. Tell the user that this separate window runs the engine safely and must remain open during play; show its link/status from Arena and accessible heading/status in the companion. Use a modest default size, but allow normal focus, movement, resizing and multi-monitor behavior—no hidden-window trick. Popup-blocked is an understandable recoverable state: “Your browser blocked the Lc0 engine window. Allow popups for CAISSA, then retry.” Accidental closure fails the Lc0 participant closed; no automatic Stockfish substitute or fabricated move.

Match window-close/runtime failure policy: stop the clock/search, label the game **aborted due to Lc0 engine failure**, retain legal moves as an interrupted record if ordinary Arena records support that, release both roles, and do not award a chess result without an approved forfeit rule. Tournament policy: pause advancement, mark the affected pairing **incomplete/engine failure**, preserve prior standings and completed games, offer explicit retry/skip/abort per published tournament rules, and do not insert `½–½` or a win merely because the engine failed. The certified `½–½` Preview continuation was **intentional adjudication**, not a failure fallback. Role switching, `ucinewgame`/RESET, reuse within the safe session policy, draw and continuation need final production smoke with one Lc0 plus Stockfish participants; never allow two Lc0 participants initially. Keep the Stockfish evaluator; do not add an Lc0 evaluator for first release.

For minimal truthful Engine Details at selection, show **Lc0**, **0.33-dev**, **CPU/WASM**, **Maia 1100**, **Experimental**, and **Desktop**. A broader Engine Details UI is outside this review and not a prerequisite to display the truthful participant name and availability reason.

Reloading the main Arena ends its current **local** Match/Tournament state. Show a pre-reload warning where practical, attempt `sendBeacon`/best-effort termination, and rely on short server-side liveness expiry plus scheduled cleanup when unload delivery fails. Do not imply that an old game can resume after reload and do not add Match persistence solely for Lc0. User-facing terminal messages should map internal categories without exposing tokens, user IDs, raw SQL or stack traces: unsupported browser (“Lc0 requires a supported desktop browser”), popup blocked, runtime load/verification failure, relay unavailable, disconnected/reconnecting, STOP timed out, engine window closed, and session expired. Provide Retry only when a new session is safe; distinguish network hash failure from generic download failure for support logs, not by displaying raw hashes to players.

## Supply chain, licensing and patch policy

**PIN AND FREEZE** the first release on Lc0 `v0.33.0-dev+git.482bb4a`, source commit `482bb4a830287b726ebe7d42f14ab7f5f17c18a0`, CPU/WASM, CSSLab Maia 1100 v1.0 (1,313,193 bytes and pinned SHA-256 above). Freeze first, pursue upstream acceptance separately, and upgrade only with a clean pinned source checkout, patch `--check`, reproducible build, hash diff, protocol/lifecycle/race tests, physical browser matrix, and fresh Preview certification. Do not track a moving upstream branch for production.

## Operations, observability and abuse controls

Emit structured, low-cardinality metrics by deployment/build, browser family/version, provider and error category: creates/claims, READY success/failure and init latency, STOP ACK/result latency, cleanup latency/evidence, valid-live `SESSION_GONE`, `STOP_TIMEOUT`/`STOP_RESULT_TIMEOUT`, forced termination, worker crash, network hash failure, auth/origin rejection, reconnects, lease expiry, active/expired sessions, relay/db errors, SSE duration/turnover, INFO received/accepted/dropped, JSONB read/write and asset egress. Include a random correlation ID and sanitized session ID for incident joins. **Never log** Clerk JWT, claim/reconnect/engine bearer, service key, full state JSON or unbounded PV/move history. Tombstones retain minimal phase, reason, server time, lease/cursor/sequence, build and correlation metadata; retention and access must be approved. Preview EAE-013A audit uses a trigger so uninstrumented direct deletes become `UNKNOWN` rather than disappearing.

Suggested first-rollout alert policy, subject to baseline tuning: immediate page on any valid-live `SESSION_GONE`, any `UNKNOWN` delete, any normal-path forced kill, or missing cleanup job for two intervals; investigate STOP timeouts above 0.5% of active searches over 15 minutes, READY success below 99%, p95 selection→READY above 10 s, p95 STOP above 5 s, p95 cleanup above 5 s, active sessions above 80% of admission cap, relay/database 5xx above 1%, or expired rows accumulating beyond two cleanup intervals. Break down intent/fault-injection metrics so deliberate crash tests do not page as normal operation. Define on-call owner, runbook, test-user deletion, replay-safe drain, and daily capacity/cost dashboard before Stage 1.

Initial proposed admission—not yet implemented—is **one live Lc0 session per authenticated user and one Lc0 participant per competition**, at most three creates/minute and 20/hour/user, ten accepted commands/s/session, <=4 persisted INFO/s/session, <=6 reconnects/minute with exponential backoff, strict raw-body/PV/event caps, and a small operator-set global active-session cap (start at 10, raise only after observed load tests). Per-IP/ASN and global edge limits complement—not replace—Clerk/account limits; keep STOP/QUIT/CLEANUP reachable under telemetry throttling. Reject over-limit actions *before* full-state CAS. The exact thresholds are rollout proposals to benchmark and adjust for accessibility/network variance, not certified production limits.

## Rollout, independent kill switch and exit gates

Production `LC0_ARENA_ENABLED=false` (or an equivalent **server-authoritative dynamic** flag) must default off independently of SF18/SF19. A kill switch must immediately block **new** Lc0 session admission/provider selection while allowing bounded STOP/QUIT/CLEANUP and revoking/draining current sessions with known reasons; test it without rolling back Arena or Stockfish. Keep a deployment/config rollback of the isolated runtime and relay, a database migration rollback plan, and immutable previous asset manifests. A dashboard toggle that only hides UI but leaves create/claim endpoints open is insufficient.

Stage 0: dark deployment, flag off, production-origin/header/CSP/CORS/Clerk/DB/asset/cron smoke with internal synthetic accounts and no public availability. Stage 1: internal/admin allowlist, monitored real Chrome/Edge desktop Match/Tournament, long sessions, window close/reload, fault drills and rollback. Stage 2: small explicit Experimental opt-in with a hard global cap and support messaging. Stage 3: supported desktop cohort only after weeks of acceptable SLO/cost/error evidence. Mobile, Safari, Firefox and a broad rollout remain separate decisions.
